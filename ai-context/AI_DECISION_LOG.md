# 决策记录：旅行规划 Agent 接入高德地图


日期：

2026-10-13


等级：

Level 2（新增模块与外部依赖，无数据库结构变化）


决策：

为旅行规划 Agent 接入高德地图 Web 服务，
补齐活动坐标、真实通勤时间与逐日天气。


原因：

模型不掌握真实地理距离，生成的行程会出现「同一天跨越几十公里」
这类不可用方案。接入地图数据后可以：

1. 给出可执行的通勤方式、距离与耗时
2. 校验行程布局并自动重排一次
3. 提供逐日天气，便于调整户外安排


影响范围：


新增文件：

lib/agents/travel/amap.ts

lib/agents/travel/amap.test.ts


修改文件：

lib/agents/travel/types.ts      新增 coordinates / address / commuteFromPrevious / commuteLegs / weather / mapEnriched

lib/agents/travel/planner.ts    接入地图增强、布局校验与一次重排

lib/agents/travel/prompt.ts     新增 location 必须可检索的硬性要求

components/travel/PlanView.tsx  展示通勤与天气

app/travel/page.tsx             运行状态新增「地图与天气」一项


配置：

环境变量 AMAP_WEB_KEY。未配置时静默跳过，不产生任何请求。


关键实现决策：


1. 地理编码优先于 POI 搜索。搜索服务月额度仅 5000 次，
   地理编码属 15 万次的基础 LBS 配额，更适合逐点解析。

2. 多方式对比。高德公交方案常给绕行路线，只按直线距离选单一方式
   会得出「同片区内 8 公里耗时 75 分钟」这类失真结果。
   实现为：并行查询候选方式（近距离加步行、始终含公交），
   取耗时最短；若仍超过 45 分钟再补查驾车。

3. 通勤段只在「相邻且双方都有坐标」时生成。
   中间活动定位失败时断开链条，避免把不相邻的两个地点配对，
   否则会出现「机场 → 市区 17 公里」这种吞掉中间行程的结果。

4. 布局校验与一次重排。拿到真实通勤后检查两件事：
   单段是否超过 60 分钟；当天活动点相对中位数中心的偏离是否超过 30 公里。
   不达标则带着具体问题（第几天、哪两个点、实测多少分钟）重新生成一次，
   重排后复检，只有问题减少才采纳。

5. 失真过滤。超过 120 分钟的公交方案判定为接口失真并丢弃。


实测效果（北京 → 三亚，5 天）：


接入前：最长市内通勤 151 分钟，存在 60 公里级跨区段

接入后：12 段通勤，最长 48 分钟，超限 0 段

方式分布：驾车 8 / 公交 3 / 步行 1

重排机制触发一次：布局问题由 2 处减少到 0 处


测试结果：

类型检查通过、ESLint 通过、460 项测试通过（旅行模块 130 项）、
生产构建通过。

# 决策记录：旅行规划体验完善（流式进度 + 地理编码可靠性）


日期：

2026-10-13


等级：

Level 2（接口行为与数据质量改进，无数据库结构变化）


## 决策一：生成过程改为流式返回进度


问题：

一次生成要调用大模型并发出数十次地图请求，实测 40-60 秒。
普通 JSON 响应期间页面毫无反馈，用户会以为页面卡死而重复点击，
既影响体验又浪费配额。


决策：

POST /api/travel/plan 支持 Accept: application/x-ndjson，
每完成一个阶段推一行 JSON；前端逐行解析并实时显示阶段进度。


为什么用 NDJSON 而不是 SSE：

SSE 依赖 EventSource，而它不支持 POST 请求。
用 fetch + ReadableStream 读 NDJSON 更直接，也不需要心跳包。


实现要点：


1. 普通响应与流式响应共用同一段生成逻辑（runGenerate），
   避免两条路径行为不一致。

2. 响应头带 X-Accel-Buffering: no，防止 Nginx 缓冲导致
   所有进度一次性到达。

3. 流式带 180 秒超时兜底，避免连接被长期占用。

4. 六个进度阶段：校验参数、查询价格、编排行程、
   获取地图数据、重新编排、生成最终方案。


实测：

curl -sN 可逐行看到进度，Nginx 未缓冲。


## 决策二：地理编码限定改用 adcode


问题：

用城市名做限定会解析到外省同名地点，生成错误的通勤。


决策：


1. 先解析城市拿到 adcode，后续地点与公交查询都用 adcode。

2. 对返回结果的 adcode 前缀做校验，越界结果直接丢弃。


理由：

错误坐标比缺失坐标更危险——缺失只是少一条数据，
错误会生成看似合理的假信息，用户无从分辨。


实测（杭州→重庆，5 天）：


修复前：30 个活动出现 5 处以上跨省错配
（贵州、辽宁、河南、湖南、广东）

修复后：27 个坐标全部在重庆，越界 0


## 决策三：地图查询采用受控并发 + 退避重试


问题：

并发过高打爆高德单 Key QPS 限制（错误码 10021），
异常被 catch 成 null 后误判为地点不存在，
坐标命中率一度只有 15%。


决策：

地理编码并发降为 2、通勤查询并发降为 2，
并对 10021 做退避重试（600ms、1500ms）。


实测：


修复前：坐标命中率 15%（4/26）
修复后：88% 至 100%，地图阶段总耗时约 16 秒


## 阶段性成果（杭州→重庆，5 天）


活动 30 个，27 个成功定位且全部在重庆

通勤 18 段，最长 45 分钟，无超限段

端到端耗时约 60 秒，其中模型约 48 秒、地图约 16 秒


后续可优化方向：

模型耗时占 75%，是主要瓶颈。若需进一步缩短总时长，
应减少布局重排触发频率，而非继续优化地图查询。

# 决策记录：打车费按里程估算并计入交通科目


日期：

2026-10-13


等级：

Level 2（预算算法调整，无数据库结构变化）


问题：

通勤中存在驾车段，但预算里没有对应的市内交通支出，
这笔钱全部落在「备用金」里，让备用金虚高、交通科目偏低。


调研结论：

实测高德 v3 驾车接口的返回字段只有
distance / duration / strategy / tolls / toll_distance /
steps / restriction / traffic_lights，
**没有 taxi_cost**，无法直接取用接口报价。


决策：


1. 按里程估算打车费：
   起步价 13 元（含 3 公里）+ 超出部分 2.6 元/公里。
   这是国内多数城市的通用计价方式，
   数值可解释、可调整，比留空更接近真实。

2. 明确标注为「按里程估算」，
   不写成「高德驾车方案估算」——高德并未返回该数据，
   标注必须与实际来源一致。

3. 计入「交通」科目：

   预算在询价后算好，而打车费要到地图增强后才知道，
   因此预算需重算一次。重算只重新分配金额，
   行程内容（坐标、通勤）保持不变。


## 实施中发现的连带问题


重算预算时最初误用模型草稿重建行程，
导致地图增强结果被覆盖，出现「有打车费、没有通勤」的矛盾状态。
已改为只重新定价。详见 AI_TROUBLESHOOTING_GUIDE.md
「有打车费却没有坐标与通勤」一节。


## 实测（武汉→厦门，5 天）


26 个活动全部定位，19 段通勤

驾车段打车费合计 319 元，已计入交通科目

交通科目：1400（机票估算）+ 319（打车）= 1719 元

预算分项合计仍等于总预算，逐日金额与科目一致

# 决策记录：报价来源定为估算，天气接入和风


日期：

2026-10-14


等级：

Level 2（外部服务接入，无数据库结构变化）


## 决策一：放弃实时报价，交通住宿保持估算


背景：

交通与住宿原本计划接入 Amadeus Self-Service 获取实时报价，
代码 (lib/agents/travel/amadeus.ts) 早已就绪，只缺 API 凭据。


核查结果：


1. Amadeus 自助服务门户已于 **2025 年 7 月 17 日下线**。
   官方站点公告原文：
   「Amadeus for Developers self-service portal has been
   decommissioned on July 17th, this website is for
   Amadeus Enterprise API Portal only」

2. 现存通道仅 Enterprise API，需商务合同对接，个人开发者无法使用。

3. 早期官方文档仍写着 test.api.amadeus.com，
   但该域名已无法解析；当前测试域名是
   test.travel.api.amadeus.com（企业沙箱，普通账号无凭据）。

4. 携程、去哪儿、飞猪等国内平台均不提供公开报价 API。
   艺龙、百度地图的酒店数据需企业资质。


决策：

保持估算模式。理由：


1. 架构上无损失。quoteMode 机制让方案如实标注
   「估算模式：未接入实时报价接口，价格仅供参考」，
   不会把估算价伪装成实时价。

2. 预算规划的本质是「预估总量并分配结构」，
   估算值足以支撑这一目标；实时报价的价值在于「下单前比价」，
   与本功能定位不同。

3. 真正的确定性价值在地图与天气，这两项已做实。


若将来需要实时报价：

应走企业商务对接，而不是继续寻找免费 Key。
代码已保留 Amadeus 实现，并可经 AMADEUS_HOST 覆盖接口地址，
届时只需配置凭据即可启用。


## 决策二：天气接入和风，作为高德天气的主来源


背景：

高德天气仅覆盖中国境内，且每月只有 5000 次配额；
出境行程（东京、曼谷、巴黎等）完全没有天气数据。


决策：

和风天气作为首选来源，高德作为兜底。

| | 和风天气 | 高德天气 |
|---|---|---|
| 覆盖 | 全球 | 仅中国境内 |
| 预报天数 | 10 天 | 数日 |
| 免费额度 | 5 万次/月 | 5000 次/月 |
| 语言 | 需传 lang=zh | 中文 |

两个必要配置，缺一不可：


1. QWEATHER_KEY       凭据里的 API Key
2. QWEATHER_HOST      控制台「设置 → API Host」的专属地址

只配 Key 不配 Host 会返回 403 Invalid Host，
该报错看起来像「Key 无效」，容易误判。
代码在缺 Host 时会给出明确提示。


## 决策三：认证方式暂用 API KEY，2027 年前迁移 JWT


背景：

和风控制台提示，自 **2027 年 1 月 1 日**起，
API KEY 认证方式将受请求量限制，官方推荐 JWT。


决策：

当前使用 API KEY，并记录待办。


理由：


1. 当前额度（5 万次/月）远超实际用量
   （每次生成方案约 1 次天气调用）。

2. 迁移 JWT 需要生成密钥对、上传私钥、重写签名逻辑，
   为 15 个月后的问题现在付成本不划算。


待办：

**2026 年 12 月前**完成 JWT 迁移，避免 2027 年起请求受限。

温度 22~34℃，风向风力正常，无告警
