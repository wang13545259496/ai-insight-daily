代码：

- 新增 app/travel/、app/api/travel/（页面与接口）

- 新增 TripPlan 表
- 迁移文件 20261015090000_add_trip_plan
- 变更前已备份 dev.db


文档：

- DATABASE_SCHEMA.md 新增模型说明
- CODE_MAP.md 新增模块位置
- AI_TASK_QUEUE.md 登记 TASK-006


AI调用方式：


经 lib/agents/travel/ai.ts 调用模型，
使用项目统一的 DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / DEEPSEEK_MODEL，
并启用 response_format=json_object，
不引入独立模型配置，符合 AI_API_INTEGRATION.md 方向。

1. 金额由确定性算法计算，大模型只负责行程内容，不参与算钱。
2. 报价接口不可用时降级为估算，并在方案中显式标注来源。
3. 模型输出不可用时降级为确定性模板，保证功能始终可用。

生产构建通过。

# 决策记录：旅行规划 Agent 接入高德地图


日期：

2026-10-13


等级：

Level 2（新增模块与外部依赖，无数据库结构变化）


决策：

为旅行规划 Agent 接入高德地图 Web 服务，
补齐活动坐标、真实通勤时间与逐日天气。


原因：

模型不掌握真实地理距离，生成的行程会出现「同一天跨越几十公里」
这类不可用方案。接入地图数据后可以：

1. 给出可执行的通勤方式、距离与耗时
2. 校验行程布局并自动重排一次
3. 提供逐日天气，便于调整户外安排


影响范围：


新增文件：

lib/agents/travel/amap.ts

lib/agents/travel/amap.test.ts


修改文件：

lib/agents/travel/types.ts      新增 coordinates / address / commuteFromPrevious / commuteLegs / weather / mapEnriched

lib/agents/travel/planner.ts    接入地图增强、布局校验与一次重排

lib/agents/travel/prompt.ts     新增 location 必须可检索的硬性要求

components/travel/PlanView.tsx  展示通勤与天气

app/travel/page.tsx             运行状态新增「地图与天气」一项


配置：

环境变量 AMAP_WEB_KEY。未配置时静默跳过，不产生任何请求。


关键实现决策：


1. 地理编码优先于 POI 搜索。搜索服务月额度仅 5000 次，
   地理编码属 15 万次的基础 LBS 配额，更适合逐点解析。

2. 多方式对比。高德公交方案常给绕行路线，只按直线距离选单一方式
   会得出「同片区内 8 公里耗时 75 分钟」这类失真结果。
   实现为：并行查询候选方式（近距离加步行、始终含公交），
   取耗时最短；若仍超过 45 分钟再补查驾车。

3. 通勤段只在「相邻且双方都有坐标」时生成。
   中间活动定位失败时断开链条，避免把不相邻的两个地点配对，
   否则会出现「机场 → 市区 17 公里」这种吞掉中间行程的结果。

4. 布局校验与一次重排。拿到真实通勤后检查两件事：
   单段是否超过 60 分钟；当天活动点相对中位数中心的偏离是否超过 30 公里。
   不达标则带着具体问题（第几天、哪两个点、实测多少分钟）重新生成一次，
   重排后复检，只有问题减少才采纳。

5. 失真过滤。超过 120 分钟的公交方案判定为接口失真并丢弃。


实测效果（北京 → 三亚，5 天）：


接入前：最长市内通勤 151 分钟，存在 60 公里级跨区段

接入后：12 段通勤，最长 48 分钟，超限 0 段

方式分布：驾车 8 / 公交 3 / 步行 1

重排机制触发一次：布局问题由 2 处减少到 0 处


测试结果：

类型检查通过、ESLint 通过、460 项测试通过（旅行模块 130 项）、
生产构建通过。
